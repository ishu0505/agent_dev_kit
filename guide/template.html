Agent Context Kit

Give any coding agent a map of a repo instead of the whole codebase. Decisions keep their reasons, conventions are written once, checks keep the docs true without anyone remembering to run them, and local learning docs teach people the architecture.

First time on your machine

  1. Clone the kit once

    git clone <your agent_dev_kit repo URL> ~/agent_dev_kit

    Any folder works. This page calls it KIT.

  2. Give every agent the setup skill

    sh ~/agent_dev_kit/install-global.sh

    Links one skill, agent-kit, into ~/.claude/skills (Claude Code), ~/.agents/skills (Codex, Cursor, Muse, Gemini CLI) and ~/.gemini/antigravity/skills (Antigravity). They are links, so git pull in the kit updates all agents.

Kit files are replaced on upgrade. Repo files are created once and never overwritten. Nothing is a setup-only leftover, so there is nothing to clean up.

Learning docs

Local files that teach a person the system: 00-overview.md for the whole architecture, one file per service or component in the order data flows, and one file per flow that crosses units, such as an API request, a queue worker job or a retry path. They are written in ASD-STE100 Simplified Technical English and never leave your machine.

SectionWhat it holds
Simple summaryThree to five sentences: what it does, its input and output, and what it does not do
A concrete exampleA realistic request, message or input, marked as invented, with fake ids and hosts
The exact pathNumbered steps in execution order, each naming the real function with a link to its file and line
DiagramA Mermaid flowchart or sequence diagram, error paths included
What comes outThe shape of the reply, record or event, with an example
Failure and edge casesRetries, timeouts, duplicates, what is not atomic, and the wrong assumption a reader is likely to make
NextLinks to the files to read next
QuizTwo easy, two medium and two hard questions on how the project works. Answers sit in a collapsed <details> block with the reason and the code reference
 
## Quiz

1. **Easy.** Which field selects the function the worker runs?
2. **Medium.** Why can a job finish but the caller never get the reply?
3. **Hard.** The reply is sent but deleting the message fails. What happens next?

<details>
<summary>Check your answers</summary>

1. `endpoint`. The worker looks it up in the router (`src/worker/router.py`).
2. The completion log is written before the reply is sent (`process_message()`).
3. The error is logged and suppressed, so the message can arrive again later.
</details>

Each file records the commit and the code paths it was written from. When git diff shows those paths changed, the learning-docs skill rewrites the stale parts. The docs step after each change asks for that refresh.

Never committed. The setup adds learning_docs/ to .gitignore, and the setup check blocks any commit that tracks or stages a file in it.

Keeping code and docs in sync

Two layers. The checks are fast and run on their own. The docs-sync skill reads the docs against the code, so it runs when you ask.

LayerFindsRuns
ChecksLong maps, dead paths, missing files, untracked agent files, local hook paths, tracked learning docsEvery commit and every editing turn
docs-syncA README with an old default, a map naming a removed command, a broken invariant, a learning doc that describes a removed stepOn request: before a merge, after a refactor, after pulling others' changes

  1. Run the checks

    Their failures go into the report.

  2. Find candidates with git only

    Docs whose folder has code changes newer than the doc's last commit, learning docs whose source_paths changed since their source_commit, and decisions or invariants that name code.

  3. Read and compare

    Each claim against the code diff: paths, commands, env vars, defaults, interfaces, flow steps, invariants. A claim it cannot confirm is marked unverified, not wrong.

  4. Report

    One table: doc, claim, what the code does, file:line evidence, proposed fix. check stops here.

  5. Fix (fix mode)

    Docs follow the code; code is never changed to match a doc. When a change breaks a decision or invariant, it asks whether the change was intended (new decision) or a bug. Then it reruns the checks.

Scope it with a unit path or since main to read only what a branch changed.

What runs on its own

There is no periodic command to remember. The checks run at the two moments a gap can enter the repo. Only the deeper docs-sync reading is on request.

Works in any language

The checks are one POSIX shell script that uses only git, grep and awk, so they run in any repo without adding a toolchain. What changes per language is which folders count as units, set in .agents/agent-kit.conf.

LanguageUnits usually areConfig
Gocmd/<app>, internal/<pkg>UNIT_PARENTS="cmd internal"
RustCargo workspace membersUNIT_PARENTS="crates"
C, C++CMake subdirectoriesUNIT_PARENTS="src libs"
Java, KotlinMaven / Gradle modulesUNITS="core api web"
C#, .NETOne folder per projectUNIT_PARENTS="src"
PythonPackages and servicesUNIT_PARENTS="services"
JS, TSWorkspace packagesUNIT_PARENTS="packages apps"

The Stop hook needs python3; without it the hook steps aside and the pre-commit check still runs. On Windows, run the scripts in Git Bash, and turn on git config core.symlinks true for the .claude/skills link.
