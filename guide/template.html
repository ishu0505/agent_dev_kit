Agent Context Kit

Give any coding agent a map of a repo instead of the whole codebase. Decisions keep their reasons, conventions are written once, checks keep the docs true without anyone remembering to run them, and local learning docs teach people the architecture.

First time on your machine

  1. Clone the kit once

    git clone git@github.com:ishu0505/agent_dev_kit.git ~/agent_dev_kit

    Any folder works. This page calls it KIT. On Windows, type every command on this page in Git Bash.

  2. Give every agent the setup skill

    sh ~/agent_dev_kit/install-global.sh

    Links one skill, agent-kit, into ~/.claude/skills (Claude Code), ~/.agents/skills (Codex, Cursor, Muse, Gemini CLI), ~/.gemini/config/skills (agy CLI) and ~/.gemini/antigravity/skills (Antigravity IDE). On macOS and Linux they are links, so git pull in the kit updates all agents. On Windows they are copies: run it again after each git pull.

Chosen at setup; the agent asks. Change it later with install.sh --share <mode>.

Agent files are every AGENTS.md and CLAUDE.md, every file ending in .agentk.md outside the learning docs, and .agents/, .claude/, .codex/, .githooks/. Local files are ignored through .git/info/exclude, which is never committed, so not even the ignore rule appears on GitHub. The pre-commit check blocks a commit that stages a local file. Local files exist only on that machine: a clone or another computer does not get them.

Your skills are safe, and the repo gets a clean-up first

The kit brings eleven skills (two of them, interactive-docs and arch-emulator, run only when you name them). A skill with any other name is never touched. For those it records a fingerprint at install, so it can tell whether you edited one.

House cleaning runs before setup in an existing project and before every upgrade, or on its own with agent-kit cleanup. inventory.sh lists every agent and doc file (maps, other agents' rule files, skills, commands, hooks, decisions, stray Markdown) with its git state, age and duplicates. The agent proposes keep, merge, own or remove for each one, asks you one group at a time, and removes only what you approve, with git rm.

What lands in a repo

The scripts and skills are copied from the kit, ready-made and tested. The agent writes only what is specific to the repo. Every Markdown file it writes ends in .agentk.md, so you can see what came from the kit; AGENTS.md, CLAUDE.md, GEMINI.md and SKILL.md keep their exact names, because agents load them only by those names. The kit never edits your own Markdown files, such as README.md: it reads them and reports drift.

A team repo that already has its own AGENTS.md or CLAUDE.md: the setup asks "personal or team repo?" first. In a team repo the kit works beside the team's files and never edits them; your map is AGENTS.agentk.md, connected to each agent by local files that are never committed (CLAUDE.local.md for Claude Code, AGENTS.override.md for Codex, your ~/.gemini/settings.json for Gemini). Nothing of yours reaches the team's remote.

Learning docs

Local files that teach a person the system: 00-overview.md for the whole architecture, one file per service or component in the order data flows, and one file per flow that crosses units, such as an API request, a queue worker job or a retry path. They are written in ASD-STE100 Simplified Technical English, for an intern on day one. The share mode decides whether they are pushed.

SectionWhat it holds
Simple summaryThree to five sentences: what it does, its input and output, and what it does not do
A concrete exampleA realistic request, message or input, marked as invented, with fake ids and hosts
The exact pathNumbered steps in execution order, each naming the real function with a link to its file and line
DiagramA Mermaid flowchart or sequence diagram, error paths included
What comes outThe shape of the reply, record or event, with an example
Failure and edge casesRetries, timeouts, duplicates, what is not atomic, and the wrong assumption a reader is likely to make

## Quiz

1. **Easy.** Which field selects the function the worker runs?
2. **Medium.** Why can a job finish but the caller never get the reply?
3. **Hard.** The reply is sent but deleting the message fails. What happens next?

<summary>Check your answers</summary>

1. `endpoint`. The worker looks it up in the router (`src/worker/router.py`).
2. The completion log is written before the reply is sent (`process_message()`).
3. The error is logged and suppressed, so the message can arrive again later.
</details>

Each file records the commit and the code paths it was written from. When git diff shows those paths changed, the learning-docs skill rewrites the stale parts. The Stop hook notes which ones a task made stale, and wrap-up asks you once, at the end of the task, whether to refresh them.

Local or pushed, you choose. In share mode agent or none they are ignored, and the check blocks any commit that stages one. In all or learning they are committed like code.

Keeping code and docs in sync

Two layers. The checks are fast and run on their own. The docs-sync skill reads the docs against the code, so it runs when you ask.

LayerFindsRuns
ChecksLong maps, dead paths in tables and prose, missing maps for big units, decision index out of step, untracked agent files, local hook paths, tracked learning docsEvery commit (only what it breaks), every turn that changed files, CI
docs-syncA README with an old default, a map naming a removed command, a broken invariant, a learning doc that describes a removed stepAt the end of a task (wrap-up), or on request

  1. Run the checks

    Their failures go into the report.

  2. Find candidates with git only

    stale.sh lists docs whose anchors changed: the paths a map names, a README's source_paths line, a learning doc's or a decision's source_paths. Only those are read.

  3. Read and compare

    Each claim against the code diff: paths, commands, env vars, defaults, interfaces, flow steps, invariants. A claim it cannot confirm is marked unverified, not wrong.

  4. Report

    One table: doc, claim, what the code does, file:line evidence, proposed fix. check stops here.

  5. Fix (fix mode)

    Docs follow the code; code is never changed to match a doc. When a change breaks a decision or invariant, it asks whether the change was intended (new decision) or a bug. Then it reruns the checks.

By default it reads what the branch changed (since main); give a unit path, or all.

Works in any language

The checks are one POSIX shell script that uses only git, grep and awk, so they run in any repo without adding a toolchain. What changes per language is which folders count as units, set in .agents/agent-kit.conf.
