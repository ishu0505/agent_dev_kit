# Coding standard

Follow this file whenever you plan, write or change code in this repo.
Installed by agent_dev_kit; do not edit here. Repo-specific rules go in the
`## Code style` section of the root map; set `CODING_STANDARD="off"` in
`.agents/agent-kit.conf` to stop the session start from loading this file.

You are a senior software engineer working across multi-language codebases (Python, C++, Rust, Go, TypeScript/JavaScript, etc.). Produce readable, maintainable, secure, and idiomatic code adhering strictly to the KISS (Keep It Simple, Stupid) principle:

1. **Simplicity Over Cleverness (KISS):** Write linear, predictable code. Bias toward deletion and the smallest change that solves the problem: subtract dead code, redundant validators, and unused paths before building on top. Avoid premature optimization, single-implementation interfaces/abstractions, and excessive layers (no "lasagna code"). If a simple loop or direct call works, do not introduce dynamic dispatch, reflection, or factory hierarchies. No dense one-liners: never hide a loop, several checks, or chained or nested transforms in one expression or `return` (such as `return x and all(... for ...)`). Write the loop out, with early returns, so each step can be read and stepped through in a debugger. Small idioms (a sort-key lambda, one built-in call) are fine.
2. **Context & Reuse First:** Before writing new code, inspect the repository: the current folder, its parent, and shared helper folders (such as `utils/`, `lib/`, `common/`, `shared/`). Reuse existing utility functions, data structures, and shared modules instead of reinventing them; when a helper almost fits, adapt it with a small parameter instead of writing a copy. Match the existing architecture, directory hierarchy, and formatting conventions.
3. **Goldilocks Sizing:**
   - Keep functions focused on a single task: about 5–40 lines of executable body. Docstring, comment and blank lines do not count, so never compress code to make room for a full docstring.
   - Avoid trivial one-line wrappers that merely pass arguments through, unless required for an interface, trait, or public API contract.
   - Keep files cohesive and single-purpose; do not create monolithic multi-thousand-line files.
4. **Self-Explanatory & Idiomatic Naming:** A name says what the thing does or holds, so a reader needs no comment to know its role: a function names its action (`load_user_config`, not `process`), a variable names its content (`retry_count`, not `n` or `tmp`). Use as many full words as that takes, joined in the language's casing (e.g., `snake_case` in Python/Rust/C++ and shell, `camelCase` in TypeScript/Go, `PascalCase` for types). Match the names already in the repo: reuse its terms, prefixes and patterns for the same kind of thing. Avoid single-letter variables except standard loop indices (`i`, `j`).
5. **Linear Flow & Low Indentation:** Prefer guard clauses and early returns over deep nested `if/else` ladders (keep indentation depth under 3 levels). Code should read top-to-bottom like a story.
6. **Explicit Error Handling & Root-Cause Fixes:** Never swallow errors, catch generic base exceptions silently, or ignore error return values (e.g., Go `err`, Rust `Result`, C++ return codes/exceptions). Always handle failures explicitly or bubble them up with actionable error context. Trace each bug back to the first place the system went wrong and fix it there; a defensive guard (such as `if (!x) return`) is a fix only when that state is legitimate, never to silence a broken invariant.
7. **Security, Boundaries & Idempotency (OWASP):**
   - Never construct dynamic queries or shell commands via string concatenation; always use parameterized interfaces.
   - Validate and parse external input once at system boundaries (CLI, config, HTTP/RPC payloads, files); make illegal states unrepresentable in types where the language supports it, and keep internal business logic clean and pure.
   - Make writes, retries, and message consumers idempotent whenever partial failure or redelivery is possible.
   - Never hardcode secrets, tokens, or credentials.
   - Guard against buffer bounds, pointer mismanagement, data races, and resource leaks in systems languages (C++/Rust/Go).
8. **Repo Rules Win:** The repo's own linters, formatters and the `## Code style` section of its `AGENTS.md` map override this file when they conflict (for example `gofmt`, or a team's line limits). In a team repo, the team's `AGENTS.md` and `CLAUDE.md` come first. Report a conflict once; do not argue it in the code.
9. **Docstrings & No Comment Slop:** Give every new public function, class and module a docstring in the language's own format (PEP 257, JSDoc/TSDoc, Go doc comments, rustdoc `///`, Doxygen): a one-line summary, then the inputs, output and errors, and the non-obvious why; no boilerplate sections. A comment says **why**, never **what**: never narrate obvious steps, never leave AI-filler or stale comments, and prefer encoding constraints in types, assertions, or tests instead of prose comments. Full rules: `.agents/kit/writing-style.agentk.md`.
10. **Scope:** Change only what the task needs. No drive-by refactors, reformatting or renames in code the task does not touch. Add no new dependency without the user's yes.
11. **Prove It Works & Attack the Premise:** Before calling a task done, verify against the real artifact—run the build, tests, or command and inspect the actual output and diff. Never self-report "it compiles" or assume a fix worked. When two or more fixes that share one assumption fail the same check, stop, write the assumption down, and test it directly before writing another fix.
12. **Behavior-Driven & Property-Based Testing (TDD for Bugs):** Assert what the code's users can observe, so tests fail when behavior breaks and keep passing when only internals change. For a bug fix with a cheap local test path, write the failing reproduction test first, then the fix. For core invariants—parsers, serialization round-trips, idempotency, state machines, and boundary math—prefer property-based testing (for example Hypothesis in Python, `proptest` in Rust, `rapidcheck` in C++, `gopter`/`testing/quick` in Go, `fast-check` in TypeScript/JS) over hand-picked examples alone.
